# MCP-серверы подключаются как обычные скиллы; недоверенный вывод изолируется от хоста

Система должна уметь не только инфраструктурные задачи. Вместо того чтобы писать свой скилл под каждую способность (поиск, документы, код), пишем один мост к MCP и получаем чужую экосистему. Первый подключаемый сервер — поиск.

**Мост живёт внутри скилла, а не отдельным слоем.** Скилл объявляет сервер во frontmatter (`metadata.mcp-url`) — питоновский `tools.py` ему не нужен вовсе, новая способность добавляется одним markdown-файлом. Спавн, айсберг, `/reload` и объединение доступов продолжают работать без правок, а Директору не приходится знать второе понятие рядом со «скиллом».

**Соединение открывается на каждый вызов**, а не живёт в модуле между задачами, как предполагалось при принятии решения: сессия MCP — контекстный менеджер, и долгая жизнь означала бы чинить переподключения, таймауты и протухшие сессии ради одного сэкономленного рукопожатия. Список инструментов сервер отдаёт один раз при загрузке скилла; недоступный сервер не роняет запуск — скилл остаётся плейбуком без инструментов. Ключи подставляются из окружения (`${TAVILY_API_KEY}`), в `SKILL.md` их нет.

**Риск объявляется на скилле, а не на инструменте.** У MCP-инструмента взять `Safety` неоткуда — сервер отдаёт только имя, описание и схему. Поле `metadata.mcp-safety: safe` во frontmatter `SKILL.md` ставит человек, подключивший сервер; отсутствие поля означает `DANGEROUS`, то есть подтверждение в Telegram на каждый вызов. Безопасный дефолт для чужого кода важнее удобства.

**Недоверенный вывод нельзя смешивать с доступом к хосту.** Скилл, чей результат содержит неконтролируемый текст, помечается `metadata.untrusted: "true"`, и спавн отказывает, если такому агенту одновременно выдан доступ к серверу или опасные инструменты (включая `run_skill_script`). Иначе внедрённая в веб-страницу инструкция попадает в контекст агента, чьи read-only команды выполняются без подтверждения. Директор обходит ограничение штатно — двумя спавнами, перенося результат сам; шиной между агентами он и так является. Остаточный риск признаём: недоверенный текст доезжает до Директора, а он умеет спавнить; всё меняющее по-прежнему упирается в подтверждение человека, чтения защищены только разделением контекстов.

*Обновлено 16.09.2026: с переходом на формат Agent Skills поля скилла переехали из корня frontmatter в `metadata` (`mcp-url`, `mcp-safety`, `untrusted`). Старые ключи в корне загрузчик отклоняет — иначе скилл молча потерял бы `untrusted` или стал безопаснее, чем задумал автор.*

*Обновлено 25.09.2026: разделение контекстов покрывало один навык из десяти, а недоверенный текст приносят и «свои» инструменты — логи nginx и journald, строки БД, User-Agent клиентов панели. Поэтому у чтений появился второй барьер — сетевой выход. Читающий вызов, который резолвит имя или подключается к хосту (`getent hosts`, `tls_check`, `ssh_query`), без подтверждения ходит только к хостам владельца: `NETWORK_ALLOWED` и адреса из настроек (`app/skills/network.py`). Иначе внедрённая в лог инструкция выносила данные DNS-запросом без единой кнопки. Заодно `getent` читает только базы без секретов — `getent shadow` отдавал хэши паролей в обход проверки файлов.*
