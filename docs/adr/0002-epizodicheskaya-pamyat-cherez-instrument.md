# Эпизодическая память доступна Директору инструментом, не автоинъекцией

Журнал задач писался с самого начала, но читал его только детектор повторов — Директор не мог вспомнить, как решал задачу в прошлый раз. Закрываем это, добавляя Директору инструмент `recall_experience(query)` поверх того же `tasks.db`.

**Эпизод** = интент + первая строка итогового ответа + выданные скиллы. Признак успеха в журнале остаётся, но с 07.08.2026 Директору не отдаётся: на живом журнале он был единицей в 89 задачах из 90 (см. `0006`). Первая строка берётся бесплатно: формат ответа Директора уже требует «итог одной фразой». Отдельного вызова LLM для резюме не делаем — это противоречило бы цели экономии. Неудачные задачи возвращаются наравне с успешными: «в прошлый раз так не сработало» ценно. Трасса инструментов остаётся в журнале (детектор, ради которого она писалась, удалён — см. `0004`), но Директору не отдаётся — шум.

**Считается по требованию, а не подставляется в промпт.** Автоинъекция Top-N похожих задач (как предписывал промпт-видение) ломает принцип айсберга, уже проведённый для скиллов и фактов: в промпте — оглавление, вглубь — по вызову. За тривиальные задачи не платим ничем. Риск, что модель не вызовет инструмент, лечится строкой в промпте, а не архитектурой.

**Поиск — на FTS5 из SQLite**, у которой ранжирование `bm25()` встроено. Требование «BM25 без тяжёлых векторных БД» выполняется без зависимости `rank_bm25` и без плоского `experience.json`, который пришлось бы перечитывать и переиндексировать целиком на каждый запрос.

**Кристаллизация повторов в скиллы отложена.** После появления эпизодической памяти повторяющаяся задача и так возвращает свой метод. Автогенерация плейбуков из журнала производила бы дубли способностей — LLM не знает, что похожий скилл уже есть, — а неперекрывающиеся скиллы для нас важнее скорости обучения. Вернуться к этому, когда живой журнал покажет повтор, который эпизодическая память не вытянула. *Закрыто в `0004`: плейбук пишет Директор по горячим следам задачи.*
